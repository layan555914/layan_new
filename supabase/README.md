# ASYUT AQAR current-state schema rehearsal and CRM preview

## Purpose

This branch tests a fresh local Supabase schema using the reviewed current-state baseline and previews the internal advertiser CRM. It is a schema/security rehearsal, not a production clone.

## Base migration chain

The branch carries 23 active SQL migrations:

1. 20261103140155_asyut_aqar_production_schema_baseline.sql — catalog-derived application schema snapshot captured on 2026-11-03.
2. 20261103140655_seed_asyut_aqar_marketplace_categories.sql — 11 stable marketplace categories.
3. 20261103141537_directory_admin_mutate_with_audit.sql — directory administration RPC.
4. The 18 SQL files currently present on main, dated 2026-11-04 through 2026-11-12.
5. 20261113165309_serialize_company_claim_approvals_by_entity.sql and 20261113172533_company_claim_feature_schema_reconciliation.sql — company representative claim locking and clean-install schema reconciliation.

The baseline is a squashed schema snapshot, not a recreation of the original 59 pre-November-3 migration bodies. Those old DDL changes are represented by the baseline snapshot. No empty no-op migration markers are added to this build chain.

## Advertiser CRM preview

The CRM schema draft is in `supabase/migration-templates/advertiser_crm_pipeline.sql`. It is intentionally kept outside the active migration folder until the feature review is complete.

The local rehearsal script calls `supabase migration new advertiser_crm_pipeline` using the pinned CLI, copies the reviewed template into that generated temporary migration path, and applies it only to the disposable local Supabase stack. The test therefore exercises the real Supabase CLI migration naming flow without prematurely adding the draft to the active migration chain.

The CRM creates two internal tables:
- `public.advertiser_leads`: company, developer, brokerage, office, supplier, service provider or sponsor prospects, with contact details, interest, stage, priority and next follow-up time.
- `public.advertiser_lead_activities`: append-only call, WhatsApp, meeting, visit, email and internal-note history.

All CRM tables have RLS. Admin accounts can read them; only owners can write directly. The existing `admin-approval.js` gate sends write attempts from added admins to the owner approval queue. Anonymous users have no direct table access. CRM writes are soft-archived rather than deleted.

The CRM starts empty. No real or sample leads are seeded. The management screen keeps this data separate from registered customer accounts and visitor activity.

## What is included

- Application-owned tables, columns, constraints, indexes, views, functions, triggers, RLS and grants from the November 3 catalog snapshot.
- Incremental admin, directory, owner approval, advertiser logo, sponsor, buyer notification and company-claim schema changes after November 3.
- The local-only advertiser CRM schema template, generated by the pinned CLI only in the temporary CI project.
- A separate local-only Storage bootstrap for two ASYUT AQAR buckets and six object policies.
- Local API tests for Auth, owner isolation, directory admin RPC atomicity and Storage RLS, plus SQL assertions for CRM read/write isolation and append-only activity history.

## What is deliberately not included

This branch does not copy production application rows, Auth users/sessions, admin allowlist memberships, real leads, private directory contact records, project review metadata, uploaded files, Storage object metadata, VAPID/private secrets, or personal identifiers.

The historical public seed material currently available is incomplete relative to production. The production catalog currently contains 26 areas, 89 directory sources, 73 directory entities, 37 projects and 31 opportunities. The old archived SQL seed sources cover only an earlier subset (26 areas, 32 sources, 47 entities and 23 projects), and internal directory address/phone and project-review inserts have been redacted from the public archive. Therefore this rehearsal does not claim to restore the current public directory dataset. Data recovery/seeding is a separate reviewed workstream.

## Run locally

Use the pinned Supabase CLI version from the CI workflow (2.84.2) and a Docker-compatible runtime.

```bash
bash scripts/ci/rehearse-current-state-schema.sh
```

The script creates an isolated temporary project, clears hosted Supabase access credentials from its environment, calls `supabase migration new` for the CRM draft, uses only local endpoints, and removes the local stack and temporary directory on exit.

## Production safety

- No hosted Supabase project ref, production password, API key or secret is configured in this branch.
- The rehearsal uses explicit `--local` CLI operations and only loopback API endpoints.
- It does not run `supabase db push`, `migration repair`, linked reset, or any production command.
- The baseline chain and CRM preview are for clean-install reproducibility only. They do not rewrite or reconcile the production migration ledger.
- No merge, production deployment, or live database change is part of this branch.
