# ASYUT AQAR — نتيجة استعادة واختبار مخطط الإنتاج

**تاريخ الفحص:** 3 نوفمبر 2026  
**المصدر:** قاعدة الإنتاج PostgreSQL 17.11  
**بيئة الاختبار:** مشروع Supabase الاختباري `layan-claude-test`  
**الحالة:** اختبار إنشاء المخطط الكامل في مساحة معزولة نجح، ثم تم التراجع عن كامل الاختبار.

## اختبارات التنفيذ والسلوك

تم تنفيذ الملف الموحّد داخل معاملة SQL على ثلاثة مخططات تجريبية منفصلة:
- `aqar_rehearsal_public`
- `aqar_rehearsal_private`
- `aqar_rehearsal_storage`

الاختبار لم يكتب على جداول الإنتاج ولم يستخدم بيانات مستخدم حقيقية. نجحت جميع تأكيدات SQL؛ لو فشل أي تأكيد لكانت المعاملة توقفت بخطأ بدل إكمالها.

### اكتمال المخطط والصلاحيات
- مطابقة أعداد الجداول والقيود والفهارس والدوال والعروض والمشغلات والسياسات مع المصدر.
- التأكد من أن RLS مفعل على كل جدول من جداول التطبيق الـ28.
- التأكد من أن `anon` لا يحصل على قراءة `directory_entity_private` أو استخدام مخطط `private`.
- التأكد من أن `anon` لا يستطيع تنفيذ `layan_is_admin()`، وأن `authenticated` لديه صلاحية التنفيذ المقصودة.
- التحقق من منح التسلسلات العامة ومن صلاحيات جداول التخزين.

### وظائف دليل أسيوط
- محاولة نشر جهة بلا مصدر عام: **مرفوضة** كما هو مطلوب.
- ربط مصدر عام بالجهة ثم النشر: **مقبول**.
- القراءة بدور `anon`: ظهرت المنطقة المنشورة فقط، ولم تظهر المنطقة المخفية.

### سياسات التخزين
- إدراج صورة في مجلد صاحبها: **مقبول**.
- إدراج صورة في مجلد مستخدم آخر: **مرفوض**.
- قراءة ملف المستند الخاص: صاحب الملف يرى مستنده فقط.
- حذف مستند مستخدم آخر: **مرفوض**.
- حذف المستند الخاص بصاحبه: **مقبول**.
- قراءة الزائر: صورة JPEG التي تطابق مسار السياسة فقط؛ لم يظهر مستند خاص.

### التراجع والتنظيف
تم تنفيذ `ROLLBACK` بعد الاختبارات. فحص ما بعد المعاملة أكد:
- `leftover_schemas = 0`
- `leftover_tables = 0`

لم تُترك أي جداول أو مخططات تجريبية في مشروع الاختبار.

## ما لم يتم — حدود مهمة

1. لم يتم استعادة ملفات الترحيلات الأصلية الـ59 أو التسلسل التاريخي الذي أنشأ المخطط.
2. الملف الموحّد snapshot لحالة المخطط الراهنة، وليس إعادة إنتاج تاريخ التعديلات migration-by-migration.
3. لم يتم تشغيل `supabase db pull` أو `supabase db reset` باستخدام Supabase CLI؛ أدوات `supabase` و`docker` و`psql` و`pg_dump` غير متاحة في بيئة التنفيذ الحالية. لذلك يظل اختبار Supabase CLI الكامل على مشروع جديد خطوة غير منجزة.
4. بيئة Supabase تتضمن schemas وجداول مُدارة مثل `auth` و`storage` و`extensions`. الملف الموحّد يفترض وجود البنية المُدارة القياسية في مشروع Supabase جديد؛ لا ينشئ Auth أو Storage stack بنفسه.
5. لا يتم نسخ أي صفوف من الجداول: لا Auth users أو جلسات، ولا allowlist للمسؤولين في `private.layan_admins`، ولا قرارات `private.project_decisions`، ولا مفاتيح VAPID الخاصة، ولا بيانات الشركات/العقارات/الدليل، ولا ملفات Storage. تُهيأ هذه العناصر بصورة منفصلة وبطريقة آمنة.
6. الملف الموحّد غير موجود داخل `supabase/migrations` ولا يجوز تشغيله على قاعدة الإنتاج الحالية. ينتظر تهيئة مسار CLI موثوق وإنشاء ملف migration بالطريقة الرسمية ثم اختبار reset على مشروع جديد.

## تاريخ الإنتاج وحدود التغيير

- عدد migrations المسجل في الإنتاج لا يزال 59 حتى `20261102180739`.
- لم يتم تعديل `supabase_migrations.schema_migrations` ولم يتم تنفيذ `migration repair`.
- لم يتم تطبيق أي DDL أو تعديل امتيازات أو سياسات على الإنتاج في هذه المهمة.
- دالة سجل المراجعة الذرّي `directory_admin_mutate_with_audit` ما زالت غير مطبقة على الإنتاج.
- لم يتم دمج PR #42 أو النشر، ولا تعديل الشعار أو ملفات الهوية.

**النتيجة:** أصبح لدينا snapshot كامل لمخطط التطبيق وصلاحياته وسياسات التخزين، واجتاز إنشاءه واختباره في مخطط معزول. ما ينقص قبل اعتماده كخط إعادة بناء رسمي هو اختبار CLI كامل على مشروع Supabase جديد، ثم اختيار مسار موثق لمزامنة تاريخ migrations القديم.
