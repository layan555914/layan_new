# مراجعة إصلاح سجل تعديلات دليل أسيوط العقاري

**الحالة:** مقترح جاهز للمراجعة والاختبار — غير مطبق على قاعدة الإنتاج وغير مدمج.

## المشكلة التي يعالجها

كانت لوحة إدارة الدليل تنفذ التغيير على جدول السجل أولًا، ثم ترسل طلبًا منفصلًا لإضافة أثر العملية إلى `directory_change_log`. إذا نجح الطلب الأول وفشل الثاني، تصبح البيانات معدلة دون سجل مراجعة مؤكد.

## التغيير المقترح

الملف `DIRECTORY_ADMIN_ATOMIC_AUDIT_20261103.sql` يعرّف الدالة:

`public.directory_admin_mutate_with_audit(text, text, uuid, jsonb, text)`

الدالة تنفذ تغيير السجل وإضافة أثره داخل استدعاء قاعدة بيانات واحد. أي خطأ أثناء إضافة سجل المراجعة يعيد العملية كلها إلى حالتها السابقة.

تسمح الدالة بقائمة محددة من العمليات والجداول والحقول فقط:

- تعديل الجهات والشركات والمشروعات والمناطق والطروحات والمصادر.
- إضافة مصدر جديد.
- ربط مصدر بجهة أو مشروع أو طرح.
- لا تسمح بالحذف، ولا تقبل أسماء جداول أو حقول اعتباطية.

## ضوابط الأمان

- `SECURITY INVOKER`: تنفذ الدالة بصلاحيات المستخدم المستدعي وتظل سياسات RLS مطبقة.
- تتحقق من `auth.uid()` ومن `public.layan_is_admin()` قبل أي تغيير.
- تم سحب `EXECUTE` من `PUBLIC` و`anon` ومنحه إلى `authenticated` فقط.
- قائمة الجداول والحقول مسموحة صراحةً، وأسماء الحقول تُقتبس قبل إدراجها في SQL الديناميكي.
- لا تتضمن الدالة تغيير امتيازات الجداول أو سياسات RLS القائمة.

## تحديث الواجهة

تم تعديل `directory-admin.js` لتستخدم استدعاء RPC واحدًا لكل من:
- حفظ/اعتماد/إخفاء/أرشفة السجلات.
- إضافة مصدر وتحديثه.
- ربط مصدر بسجل.

أزيل مسار الكتابة المنفصل إلى `directory_change_log` من هذه العمليات.

## الاختبار المنفذ

تم تشغيل SQL المقترح في مشروع الاختبار `layan-claude-test` داخل معاملة واحدة مؤقتة، مع جداول اختبار معزولة ثم تنفيذ `ROLLBACK` في النهاية.

النتائج:
- إضافة مصدر مع سجل مراجعة: PASS.
- تعديل سجل مع حفظ القيم قبل/بعد: PASS.
- ربط مصدر بسجل مع أثر مراجعة: PASS.
- فرض فشل إدراج أثر المراجعة والتحقق أن تعديل السجل تراجع معه: PASS.
- عدد سجلات المراجعة الناجحة في الاختبار: 3.
- بعد التراجع لا تبقى الجداول أو البيانات التجريبية.

تم تحديث اختبار المتصفح `tests/e2e/directory.spec.mjs` ليحاكي نقطة RPC الجديدة، ويتحقق من رسالة فشل العملية دون تغيير بيانات السجل في المحاكاة.

## مانع ترتيب النشر — لا تتجاوزه

قاعدة الإنتاج تحتوي على تاريخ migrations في `supabase_migrations.schema_migrations` (ومن أحدث الإصدارات المسجلة `20261102180739`)، لكن فرع `main` في GitHub لا يحتوي حاليًا على مجلد `supabase/migrations` أو ملفات تلك الإصدارات؛ مجلد `supabase` يحتوي فقط على Edge Functions.

لذلك لم أضع ملف SQL منفردًا داخل `supabase/migrations`، ولم أطبق الدالة على قاعدة الإنتاج. إضافة migration منفردة إلى مجلد غير موجود مع غياب تاريخ التغييرات السابق قد تعطي انطباعًا خاطئًا بأن المستودع يعيد بناء قاعدة البيانات كاملة.

قبل اعتماد التغيير يجب:
1. استعادة/مطابقة ملفات migrations السابقة من مصدرها الموثوق، أو اعتماد إجراء موثق لمزامنة تاريخ قاعدة الإنتاج مع المستودع.
2. إدراج SQL المقترح كـ migration بعد مراجعة التاريخ.
3. تطبيقه على بيئة اختبار يمكن تشغيل لوحة الإدارة عليها.
4. التأكد من أن RPC منشورة قبل نشر نسخة الواجهة التي تستدعيها.
5. تنفيذ اختبار تسجيل الدخول الفعلي بحساب مسؤول والتحقق من الحفظ والنشر وسجل المراجعة.

## حدود هذه المراجعة

- لا توجد أي تغييرات على قاعدة الإنتاج.
- لا توجد تغييرات على بيانات الدليل أو صلاحيات المستخدمين أو RLS.
- لم يتم اختبار تسجيل دخول فعلي بحساب مسؤول؛ لا تتوفر جلسة مسؤول في الاختبار الحالي، ولم أطلب كلمة المرور.
- لم يتم الدمج إلى `main` أو نشر الموقع.
- مستقل تمامًا عن PR #40 وPR #41.
