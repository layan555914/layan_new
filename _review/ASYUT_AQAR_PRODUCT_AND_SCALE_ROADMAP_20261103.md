**تاريخ الإعداد:** 3 نوفمبر 2026  
**الحالة:** وثيقة تخطيط ومراجعة فقط — لا تنفّذ ترقية أو نقل استضافة أو تعديلًا على الإنتاج.

## 1) الهدف
تجهيز أسيوط عقار لتعمل كمنظومة عقارية محلية قابلة للنمو، مع فصل واضح بين:
- استضافة الموقع والواجهة.
- قاعدة البيانات والمصادقة والتخزين.
- ملفات وصور العقارات والمشروعات.
- خدمات البريد والتنبيهات والخرائط.
- أدوات المراقبة والنسخ الاحتياطي والأمان.

هذه الخارطة تجمع قرارات البنية التحتية مع قائمة المنتجات المقترحة، وتمنع تكرار أعمال موجودة بالفعل في طلبات المراجعة المفتوحة.

## 2) الوضع الحالي المعروف — خط أساس وليس اختبار تحمّل
### التطبيق
- التطبيق الحالي واجهة HTML/CSS/JavaScript ثابتة، ويتصل بـ Supabase للمصادقة وقاعدة البيانات والتخزين والوظائف الطرفية.
- مستودع الكود: `layan555914/layan_new`.
- ملف `config.js` يحتوي عنوان مشروع Supabase ومفتاح Publishable فقط؛ يمنع وضع Service Role أو أي Secret في المتصفح.
- الموقع مرتبط حاليًا بنطاق `layan-eg.com`، المسجّل لدى IT PLUS. يجب الحفاظ على النطاق والشعار والهوية الحالية.

### Supabase
- مشروع الإنتاج: `ebyhwqkmhxbgocngpqfe` — الحالة المرصودة ACTIVE_HEALTHY.
- مشروع الاختبار: `wisnmlbefdrkcbbqvdlg` — الحالة المرصودة ACTIVE_HEALTHY.
- المشروعان تحت مؤسسة Supabase على خطة Free وقت إعداد الوثيقة.
- فحص مشروع الاختبار أظهر 26 جدولًا عامًا و74 فهرسًا وحجم قاعدة يقارب 15 MB. هذه لقطة لحجم الاختبار فقط، ولا تثبت سعة الإنتاج أو قدرة تحمّل المستخدمين.
- محاولة إنشاء فرع Supabase منفصل رُفضت لأن ميزة Branching تتطلب Pro أو أعلى. يوجد مشروع اختبار منفصل حاليًا؛ يمكن مواصلة الاختبار عليه مع ضبط البيانات والاعتمادات، أو اعتماد Branching بعد موافقة التكلفة.
- لا توجد أي موافقة في هذه الوثيقة على ترقية الخطة أو تغيير قاعدة الإنتاج.

### الاستضافة

- GitHub يوضح أن Pages غير مخصص أو مسموح به كاستضافة مجانية لتشغيل نشاط تجاري عبر الإنترنت أو خدمة SaaS، كما يذكر أن Pages لا ينبغي استخدامه لمعاملات حساسة مثل إرسال كلمات المرور. لذلك يجب التخطيط لنقل استضافة الإنتاج إلى استضافة تجارية قبل تشغيل المنصة تجاريًا أو الاعتماد عليها في تدفقات حساسة. راجع: https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features
- لا يتم تحويل DNS أو ربط النطاق بإنتاج Vercel قبل اختبار النسخة، ومراجعة قيم DNS التي يعرضها Vercel، ووجود خطة رجوع مكتوبة.

## 3) قرارات البنية التحتية المقترحة
### 3.1 استضافة الموقع والتوزيع
**الاتجاه الموصى به:** Vercel Pro أو استضافة تجارية مكافئة، مع إبقاء GitHub مصدر الكود وإدارة التغييرات.

المتطلبات:
1. إبقاء كل Pull Request على Preview منفصل.
2. استخدام Production deployment محمي بموافقة صريحة، وعدم النشر المباشر لمجرد إنشاء فرع أو PR.
3. اختبار صفحات الموقع والروابط وRTL والهواتف والكمبيوتر، واختبار الدخول والاستعادة ورفع الصور والإعلانات قبل أي تبديل للنطاق.
4. اختبار الدومين المؤقت أولًا، ثم ربط `layan-eg.com` في خطوة مستقلة بعد الموافقة.
5. عند الانتقال، تحديث سجلات الموقع المطلوبة فقط حسب تعليمات الاستضافة الجديدة؛ الحفاظ على سجلات Resend والبريد وNS وأي سجلات أخرى غير مرتبطة بالموقع.
6. ضبط تنبيهات الإنفاق وحدود الاستخدام قبل تفعيل خطة مدفوعة. لا تُفترض تكلفة نهائية من سعر المنصة الأساسي وحده.

### 3.2 قاعدة البيانات والخدمات الخلفية
**الاتجاه الموصى به:** الاستمرار مع Supabase حاليًا، ثم الترقية عندما نحتاج إلى بيئة Branching أو موارد وضمانات تشغيلية أعلى.

خطة التنفيذ:
- الاحتفاظ بمشروع إنتاج مستقل ومشروع اختبار مستقل؛ لا تستخدم بيانات عملاء الإنتاج في الاختبارات.
- اعتماد migrations محفوظة في Git ومراجعتها قبل التنفيذ، مع اختبارها على مشروع الاختبار أولًا.
- استخدام Supabase Branching عند الحاجة إلى بيئة مستقلة لكل PR وبعد الموافقة على Pro وتكاليف الفروع المتغيرة؛ توضح وثائق Supabase أن Branching متاح على Pro، وأن الفروع لها تكاليف استخدام مستقلة حسب الموارد والمدة.
- مراجعة سياسات RLS وامتيازات SQL على جميع الجداول المكشوفة، ومراجعة Views وRPC وStorage وسياسات الملفات الخاصة.
- مراجعة الاستعلامات والفهارس بناءً على خطط التنفيذ الفعلية، لا حذف الفهارس لمجرد أن فحصًا مبكرًا وصفها بأنها غير مستخدمة.
- استخدام Connection Pooling عندما يناسب نمط الاتصالات، ومراجعة حدود الاتصالات قبل زيادة الحمل.
- فصل الصور والمرفقات عن بيانات الصفوف، وضبط أحجام الصور والنسخ المصغرة والتخزين المؤقت.
- الاحتفاظ بنسخ احتياطية قابلة للاستعادة، ثم تقييم PITR عندما تصبح قيمة البيانات وحجم النشاط تستدعي ذلك.
- عدم إدخال Redis أو خادم VPS أو Read Replica إلا بعد قياسات تثبت الحاجة.

### 3.3 البريد والتنبيهات
- إكمال التحقق من نطاق الإرسال في Resend (DKIM وسجلا CNAME) قبل الاعتماد عليه.
- بعد التحقق، إعداد SMTP/مزود البريد في إعدادات Supabase من خلال واجهة الإعدادات الآمنة، واختبار رسائل التسجيل والاستعادة وتغيير البريد.
- عدم تفعيل استقبال البريد أو Resend Forge ما لم تظهر حاجة منفصلة وموافقة.
- معالجة حدود الإرسال ومعدلات التكرار برسائل واضحة، مع عدم إظهار نجاح إرسال غير مؤكد.
- تدقيق Push subscriptions ومفاتيح VAPID وصلاحياتها قبل إطلاق تنبيهات المتصفح.

### 3.4 المراقبة والأداء
إنشاء لوحة تشغيل داخلية ومؤشرات متابعة تشمل:
- زمن استجابة الواجهة وطلبات قاعدة البيانات، خصوصًا P95.
- أخطاء JavaScript وHTTP وطلبات Supabase وEdge Functions.
- استهلاك CPU/الذاكرة والاتصالات وحجم قاعدة البيانات.
- مساحة التخزين وحركة نقل البيانات والوظائف الطرفية ورسائل Realtime.
- معدل نجاح التسجيل وتأكيد البريد واستعادة كلمة المرور ورفع الملفات.
- عدد الإعلانات المنشورة والمعلقة والمرفوضة ومعدل الإبلاغ عن الإعلانات.

تُضبط تنبيهات إنفاق واستخدام عند الاقتراب من حدود الخطة، وتُجرى مراجعة موارد عند استمرار الاستهلاك المرتفع أو تدهور P95 أو ظهور أخطاء اتصالات. لا يتم اختيار حجم Compute أو شراء خدمة قبل أخذ القياسات.

## 4) خارطة ميزات المنتج
> هذه بنود Backlog. أي ميزة موجودة جزئيًا تُراجع وتُستكمل بدل إنشاء نسخة مكررة.

### أولوية 0 — تثبيت الأساس قبل إضافة حمل جديد
- استكمال مراجعة أمان الدليل العقاري وصلاحيات الجداول وRLS وACL.
- إكمال سجل التدقيق غير القابل للتعديل، وربط كل تعديل إداري بمستخدم ووقت وسبب.
- التحقق من إنشاء المشروعات كسجلات مخفية Draft فقط حتى اعتماد الإدارة.
- مراجعة تدفق التسجيل وتأكيد البريد واستعادة كلمة المرور ورسائل Resend وحدود الإرسال.
- اختبار رفع الصور والمستندات، والتأكد من بقاء مستندات الملكية خاصة.
- تدقيق البحث والفلاتر والمفضلة وتنبيهات المشتري الحالية قبل توسيعها.
- استكمال اختبارات المتصفح الحقيقية على شاشات الهاتف والكمبيوتر، وعدم اعتبار الفحص الساكن بديلًا لاختبار رحلة المستخدم.

### أولوية 1 — الخريطة والبحث الجغرافي
- استكمال خريطة العقارات وربطها بالإعلانات التي تملك إحداثيات صحيحة.
- استكمال خريطة دليل أسيوط للجهات والشركات والمشروعات والمناطق، مع فصل نقطة مرجعية للمنطقة عن عنوان موثق لجهة.
- إظهار مصدر الموقع ودرجة التحقق وتاريخ المراجعة؛ لا تُنشر إحداثيات تخمينية على أنها عنوان مؤكد.
- إضافة طبقات خدمات قريبة (تعليم، صحة، نقل، مرافق) فقط من مصادر قابلة للتحقق والتحديث.
- مرشحات حسب المدينة والمنطقة ونوع العقار والسعر والمساحة ونوع المعاملة.
- الحفاظ على وظائف الخريطة الحالية وعدم كسر تجربة البحث التقليدية عند تعطل مزود الخرائط.

### أولوية 2 — أدوات قرار المشتري
- مقارنة حتى 3 عقارات بخصائص موحدة: السعر، المساحة، المنطقة، التشطيب، الدور، حالة الوحدة وشروط التنازل.
- تطوير البحث المحفوظ والتنبيهات بناءً على تفضيلات المستخدم، مع منع التنبيهات المكررة وتوفير إيقافها.
- صفحة مشروع موحدة تربط المطور والمصادر والموقع والوحدات والعروض المرتبطة.
- حاسبة تكلفة شراء/تنازل/أقساط توضح افتراضاتها ولا تخفي الرسوم أو الالتزامات.
- طلب معاينة منظم بموافقة صاحب الإعلان وبدون كشف بيانات غير لازمة.

### أولوية 3 — معلومات السوق
- مؤشر استرشادي لأسعار العرض حسب المنطقة ونوع العقار والمساحة، مع تاريخ التحديث وحجم العينة ومصدر البيانات.
- عرض نطاقات وأسعار إعلانات منشورة لا ادعاء أنها أسعار صفقات بيع فعلية؛ يجب التمييز بوضوح بين سعر العرض وسعر التنفيذ.
- تقارير اتجاه الطلب والمشاهدات والعروض حسب المناطق، مع إخفاء البيانات الشخصية.
- استكمال قاعدة الشركات والمشروعات والمناطق بمصادر وروابط وتاريخ تحقق وحالة نشر ومراجع مراجعة.

### أولوية 4 — الوسائط والخدمات
- دعم فيديو قصير وجولات 360 درجة للعقار مع ضغط وتحويل الصور ومقاطع الفيديو قبل العرض.
- تطوير سوق التشطيب والديكور والصيانة والأثاث والخدمات العقارية، مع ملفات مقدمي الخدمة وطلب عرض سعر وتقييمات موثقة.
- خدمة طلب تقييم عقار أو معاينة فنية عبر مقدم خدمة معتمد، مع توضيح أن التقييم ليس ضمانًا للسعر.
- دليل جهات التمويل والتمويل العقاري بوصفه إحالة معلوماتية فقط، دون تقديم وعد بموافقة تمويل أو استشارة مالية غير مرخصة.

### أولوية 5 — المساعد الذكي والثقة
- مساعد عقاري يفهم طلب المستخدم باللهجة المصرية ويبحث داخل بيانات المنصة الفعلية فقط.
- يجب أن يعرض نتائج موجودة بالفعل ويشرح أسباب المطابقة، ويقول بوضوح عند عدم وجود نتائج؛ لا يخترع عقارات أو أسعارًا أو توافرًا.
- كشف إعلانات مكررة عبر تشابه الصور والنصوص وأرقام التواصل، وإحالتها للمراجعة بدل الحذف الآلي.
- زر إبلاغ عن إعلان أو جهة مع مسار مراجعة موثق.
- توثيق الحسابات وأرقام الهاتف والجهات وفق خطوات متدرجة لا تعطي شارة موثوقية بلا تحقق.

### أولوية 6 — أدوات الإدارة والإيراد
- لوحة مؤشرات للإدارة: الطلبات، الإعلانات، المناطق الأكثر نشاطًا، جودة البيانات، مصادر الدليل، ومعدلات البلاغات.
- تنبيه انتهاء الإعلان أو طلب تجديده، مع حفظ سجل الحالة.
- مساحات إعلانية وطلبات تمييز للشركات والخدمات من خلال مراجعة الإدارة والتواصل عبر واتساب، دون نشر أسعار أو باقات أو مدد ثابتة قبل اعتمادها.
- الإعلانات العقارية العادية تظل مجانية، ولا توجد عمولة على إتمام البيع أو التنازل.
- لا تُضاف مدفوعات إلكترونية أو تحصيل تلقائي قبل سياسة مالية معتمدة واختبار أمني وموافقة منفصلة.

## 6) معايير قبول عامة
- لا تغيير إنتاجي أو ترقية مدفوعة أو تعديل DNS أو نشر دون موافقة مستقلة.
- لا نقل أو تعديل بيانات إنتاج ضمن اختبارات التحمل.
- كل Migration تُختبر على الاختبار أولًا، مع مراجعة خطة الرجوع والقيود.
- لا تعرض الواجهة بيانات غير معتمدة أو مواقع مخمّنة أو أسعار صفقات غير متاحة.
- لا أسرار في Git أو المتصفح أو سجلات الاختبار؛ يستخدم Publishable key في المتصفح فقط.
- RLS مفعّل ومراجع على الجداول المكشوفة، والملفات الخاصة لا تُعرض بروابط عامة دائمة.
- اختبارات الهاتف والكمبيوتر والروابط والمصادقة والبحث والرفع والخريطة قبل أي دمج أو نشر.
- الحفاظ على الشعار الأصلي والهوية والألوان RTL.
- كل تقرير يميز بين ما نُفّذ فعلًا وما هو مقترح أو لم يُختبر.
