# مراجعة جاهزية لوحة الشركة وربط المشروعات — 2026-11-17

هذه المراجعة قراءة فقط لفرع لوحة الشركة وللمخطط الحالي في مشروع Supabase الإنتاجي. لا تتضمن أي تعديل على قاعدة البيانات أو الصلاحيات أو البيانات.

## حالة معاينة لوحة الشركة

- طلب المراجعة: PR #155.
- الصفحة `company-dashboard.html` معاينة تصميم وليست لوحة تشغيلية.
- التنسيق يستخدم عائلة الألوان والخطوط الموجودة بالفعل في صفحة الشركات الحالية، ويحافظ على ملف الشعار الأصلي.
- الأقسام المعروضة تشمل نظرة عامة، بيانات الشركة، المشروعات، الوحدات والإعلانات، فريق العمل، والمراجعات.
- لا يوجد اتصال حالي ببيانات الشركة أو جلسة المستخدم أو عمليات حفظ داخل صفحة المعاينة.
- لا يجوز عرض أرقام افتراضية باعتبارها أرقام الشركة؛ يجب أن تأتي المؤشرات من سجلات يحق للممثل رؤيتها.

## ما كشفه فحص المخطط الحالي (قراءة فقط)

الأعداد التالية هي أعداد الصفوف التي أظهرتها أداة فحص الجداول وقت المراجعة، وقد تتغير لاحقًا:

- `directory_projects`: عدد 37 سجلًا.
- `directory_project_entities`: عدد 40 علاقة بين مشروع وجهة في الدليل.
- `property_offers`: عدد 7 سجلات.
- `company_profiles`: عدد 0 سجل وقت الفحص.
- `company_claim_requests`: عدد 0 طلب وقت الفحص.
- `company_entity_managers`: عدد 0 ربط ممثل معتمد وقت الفحص.
- `company_entity_manager_members`: عدد 0 عضو فريق وقت الفحص.

### علاقات البيانات الحالية

1. `directory_project_entities` يربط المشروع بجهة من `directory_entities` ويحدد نوع العلاقة مثل المطور أو وكيل التسويق أو وكيل المبيعات.
2. لا يوجد في `property_offers` حقل `project_id` ولا مفتاح أجنبي إلى `directory_projects`.
3. يوجد في `property_offers` حقلا `project_name` و`developer_name` كنصين فقط؛ لا يكفيان لإثبات ارتباط موثوق بمشروع.
4. يحتوي `company_profiles` على `projects` من نوع JSONB، وهو محتوى وصفي/سابق أعمال وليس سجلات مشاريع مستقلة.
5. لا توجد علاقة مباشرة ظاهرة بين `company_profiles` و`directory_projects`. مسار علاقات المشروعات الحالي يعتمد على كيانات الدليل `directory_entities`.

### حدود الصلاحيات الحالية

- جداول `directory_projects` تسمح بالقراءة العامة للسجلات المنشورة والظاهرة فقط.
- إدراج وتحديث وحذف سجلات المشروعات في السياسات الحالية مقتصر على إدارة المنصة.
- `directory_project_entities` كذلك لا تسمح للشركات بإضافة أو تعديل العلاقات مباشرة؛ سياسات الكتابة الحالية للإدارة.
- إعلانات `property_offers` العامة متاحة للقراءة عندما تكون حالتها `available`، والإعلان الجديد من حساب المستخدم يبدأ `pending`.
- جداول استلام ملفات الشركات وأعضاء الفريق محمية بـ RLS، لكن وجود جداول إدارة الملف لا يعني وجود صلاحية لإدارة المشروعات أو الوحدات.

## القرار المعماري المطلوب قبل التشغيل

لا نربط الشركة بالمشروع عن طريق مطابقة الاسم النصي. يلزم نموذج علاقة صريح ومراجع:

- ملف الشركة المملوك: ربط آمن بين `company_profiles` وسجل الشركة/الكيان عند وجود تطابق موثق.
- ملف الدليل: الاستفادة من `company_entity_managers` بعد اعتماد الممثل.
- المشروع: الاحتفاظ بسجل واحد في `directory_projects`، وربط كل جهة بدورها في `directory_project_entities`.
- الوحدة/الإعلان: إضافة علاقة موثوقة بالمشروع بعد تحديد هل الأنسب حقل أجنبي اختياري على `property_offers` أم جدول ربط مستقل، مع دعم الإعلان المستقل وعدم تكرار الوحدة.
- شركات التسويق ترتبط بالمشروع كـ `marketing_agent` أو `sales_agent` فقط بعد توثيق التفويض؛ لا تُسجل كمطور.
- كل إدخال أو تعديل من الشركة يبدأ في حالة مراجعة ولا يصبح عامًا تلقائيًا.

## الخطوات الآمنة التالية

1. إكمال فحص وظائف استلام ملف الشركة وتحديثه وإدارة أعضاء الفريق الموجودة، وربط واجهة اللوحة بها دون تغيير صلاحياتها.
2. إعداد تصميم/مقترح مخطط للعلاقات والصلاحيات الخاصة بالمشروعات والوحدات، مع حالات المراجعة وسجل التغييرات.
3. اختبار المقترح على بيئة اختبار معزولة، لا على قاعدة الإنتاج.
4. عرض SQL migration وسياسات RLS وRPC على صاحب المنصة للموافقة الصريحة قبل تطبيق أي تغيير.
5. بعد الموافقة فقط: التنفيذ والاختبارات، ثم مراجعة مستقلة قبل الدمج والنشر.

- لم يتم دمج PR #155 أو نشره على الإنتاج.
